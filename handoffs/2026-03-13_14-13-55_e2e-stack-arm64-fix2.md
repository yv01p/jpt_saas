## 3. Mental Model (Most Critical Section)

**Why the current approach was chosen:**
Same ARM64 reasoning as previous handoff (no QEMU, multi-arch images, user: redis/postgres). The new layer of complexity this session: the api Docker image uses a pre-built Gradle JAR (`api/build/libs/app.jar`) copied into the image — Docker does NOT run Gradle during build. Therefore any changes to `src/main/resources/` REQUIRE a `./gradlew :api:bootJar -x test` rebuild before `docker compose build api`. This was the root cause of the longest debug cycle this session.

**Codebase Gotchas Discovered This Session:**
- `api/Dockerfile:9` — `COPY build/libs/app.jar app.jar` — the Dockerfile copies a pre-built JAR, NOT built during Docker build. Changes to Spring resources require: (1) `./gradlew :api:bootJar -x test`, (2) `docker compose ... build api`, (3) `docker compose ... up -d --force-recreate api`. Without step 1, `--no-cache` Docker builds still pick up the old JAR from disk.
- `api/src/main/resources/application.yml:41` — `spring.data.redis.url` + `spring.data.redis.password` conflict: Lettuce uses the URL as the primary config and ignores the separate `password` property when URL is set. Fix: embed password in URL as `redis://:PASSWORD@redis:6379`.
- `docker-compose.yml` (api service) — `FLYWAY_DB_USER` is never passed to the api container. Spring Boot defaults to `jpt` (from `${FLYWAY_DB_USER:jpt}` in application.yml). But a fresh Postgres has only `jpt_app` (the POSTGRES_USER). Fix: add `FLYWAY_DB_USER: ${DB_USER}` to docker-compose.ci.yml api environment.
- `docker-compose.yml` (api service) — `WORKER_DB_PASS` is also never passed. Needed for Flyway placeholder `worker_db_user_password` in V3 migration. Causes Spring Boot startup failure with unresolved placeholder.
- `api/src/main/resources/application.yml` — No `spring.security.oauth2.client.registration.*` config. The app uses `.oauth2Login()` in SecurityConfig which requires a `ClientRegistrationRepository` bean. Without OAuth2 client registrations, Spring Boot fails to start. Fix: create `api/src/main/resources/application-test.yml` with dummy Google + GitHub registrations using env var defaults.
- `api/src/test/resources/application-test.yml:1` — This file exists for Maven/Gradle tests (uses TestContainers). It takes precedence over `src/main/resources/application-test.yml` on the test classpath. The main resources version is only active in Docker (JAR runtime).
- Spring Boot takes ~100s to start on this single-CPU ARM64 host. The base healthcheck (5 retries × 10s = 50s) was too short. Added `start_period: 240s` and `retries: 10` to give it ~390s total.

**Dead Ends — Do Not Repeat These:**

| Approach Tried | Why It Failed | Evidence |
|---------------|---------------|----------|
| AMD64 SHA-pinned redis/postgres on ARM64 | exec format error — no QEMU | `docker logs jpt_saas-redis-1: exec format error` |
| `cap_drop: []` / `security_opt: []` to remove hardening | Compose merges arrays, doesn't replace | redis still failed with `operation not permitted` |
| Override nginx `ports: ["8080:80"]` | Compose merges port arrays, both bind — conflict with Caddy | nginx conflict |
| `docker run --platform linux/amd64` emulation | QEMU not installed | `exec format error` |
| `docker compose build --no-cache api` without Gradle rebuild | Copies stale JAR from disk — `--no-cache` only skips Docker layer cache, not the JAR content | `application-test.yml` missing from new image despite `--no-cache` |
| Setting `SPRING_PROFILES_ACTIVE: test` without rebuilding JAR | New `application-test.yml` was not in JAR (built before file was created) | `unzip -l /app/app.jar \| grep application` — no test yml |
| `REDIS_URL=redis://redis:6379` + `REDIS_PASSWORD=ci_test_redis` separately | Lettuce sends HELLO before AUTH when URL has no credentials | `NOAUTH HELLO must be called with the client already authenticated` |

**Key Decisions Made:**

| Decision | Rationale | Alternative Rejected |
|----------|-----------|---------------------|
| `application-test.yml` in `src/main/resources/` (not `src/test/resources/`) | Packaged in JAR; test resources version (TestContainers) takes precedence in Maven test scope | Env var `SPRING_SECURITY_OAUTH2_CLIENT_REGISTRATION_*` — more env vars to manage in compose |
| `FLYWAY_DB_USER: ${DB_USER}` in ci override | jpt_app is the only user on a fresh Postgres; jpt_admin (in .env.ci) doesn't exist yet | Separate postgres init script — more infrastructure |
| `start_period: 240s, retries: 10` | Spring Boot needs ~100s; 240 + 150 = 390s total grace | Smaller values — caused crash loop on slow ARM64 host |
| Gradle rebuild + Docker rebuild sequence | Only way to get new resources into the JAR | Cannot skip Gradle rebuild |

**Assumptions in Play:**
- The worker connects to Postgres as `jpt_worker` (WORKER_DB_USER in .env). V3 migration creates `worker_db_user` role. Need to confirm these names match.
- The worker's heartbeat file (`/tmp/worker-heartbeat`) is written within 240s of container start — not yet confirmed.
- After api is healthy, nginx will stabilize on its own (it depends on api health).
- SPRING_PROFILES_ACTIVE=test doesn't activate the TestContainers config from src/test/resources (test resources not in JAR) — confirmed correct.
